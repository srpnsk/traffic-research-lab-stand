# Network Lab

Изолированная лаборатория для исследования сетевого трафика, механизмов фильтрации и методов обхода сетевых ограничений.

## 1. О проекте

Network Lab — экспериментальный стенд на базе Docker, предназначенный для воспроизводимых сетевых экспериментов. Он позволяет генерировать трафик, наблюдать за его прохождением через промежуточный узел, исследовать поведение сетевых фильтров и сохранять результаты для последующего анализа.

Лаборатория развёртывается на VPS под управлением Ubuntu 24.04. Для запуска контейнеров используется Rootless Docker: демон работает от отдельного непривилегированного пользователя `dockerroot`, а не от `root`.

Основные цели проекта:

- исследование сетевого взаимодействия в контролируемой среде;
- изучение методов фильтрации и обнаружения трафика;
- сбор PCAP для последующего анализа в Wireshark и других инструментах;
- воспроизводимость экспериментов;
- совместная работа участников с разграничением доступа к хосту и лаборатории.

**Важно:** Rootless Docker снижает риски, связанные с управлением контейнерами, но не гарантирует абсолютную изоляцию от хоста. Все эксперименты должны проводиться в пределах разрешённой среды.

## 2. Архитектура

Лаборатория состоит из трёх контейнеров.

| Узел | Адрес | Назначение |
|---|---|---|
| `lab-client` | `10.231.10.3` | Генерация клиентского трафика |
| `lab-filter` | `10.231.10.2`, `10.231.20.2` | Маршрутизация, фильтрация и захват пакетов |
| `lab-server` | `10.231.20.3` | Серверная сторона экспериментов; тестовый HTTP-сервис на порту `8080` |

Схема взаимодействия:

```text
                  lab-client
                10.231.10.3
                      |
             lab-client-net
               10.231.10.0/24
                      |
                 lab-filter
          client: 10.231.10.2
          server: 10.231.20.2
                      |
             lab-server-net
               10.231.20.0/24
                      |
                  lab-server
                10.231.20.3
                 TCP/8080
```

Ожидаемая конфигурация сетей:

- `lab-client-net` — внутренняя сеть клиента и фильтра;
- `lab-server-net` — внутренняя сеть фильтра и сервера;
- `lab-filter` подключён к обеим сетям;
- клиент и сервер не подключаются напрямую к одной сети;
- публикация портов контейнеров на интерфейсы VPS не требуется.

Сети должны быть созданы с параметром `internal`, если это предусмотрено текущей реализацией `build-lab.sh`. Фактическую конфигурацию необходимо проверять после развёртывания.

## 3. Требования

Для развёртывания необходимы:

- Ubuntu 24.04;
- административный доступ через `sudo`;
- Rootless Docker, работающий от пользователя `dockerroot`;
- пользовательский systemd-сеанс, доступный через `machinectl`;
- пакеты `uidmap`, `dbus-user-session` и необходимые зависимости Rootless Docker;
- свободное место для образов, контейнеров и захватов;
- при использовании веб-каталога результатов — установленный Caddy и настроенный домен с HTTPS.

Для удалённой работы участников также нужны SSH-клиенты и индивидуальные пары SSH-ключей.

## 5. Установка и настройка

### 5.1. Первоначальная подготовка Rootless Docker

`00-install-rootless-docker.sh` предназначен для первоначальной установки Rootless Docker и настройки системных зависимостей.

Запускать его следует только при первоначальном развёртывании или осознанном восстановлении окружения:

```bash
sudo ./00-install-rootless-docker.sh
```

Не запускайте этот сценарий автоматически при каждом обновлении лаборатории.

После установки проверьте службу:

```bash
sudo machinectl shell dockerroot@.host /bin/bash -lc \
  'systemctl --user is-active docker.service'
```

Проверьте режим Docker:

```bash
sudo machinectl shell dockerroot@.host /bin/bash -lc \
  'docker info'
```

В выводе `docker info` должен быть подтверждён режим Rootless.

### 5.2. Настройка хоста

`10-configure-host.sh` предназначен для настройки системной части лаборатории: каталогов, вспомогательных команд, прав доступа, правил `sudoers` и системных таймеров.

Запуск:

```bash
sudo ./10-configure-host.sh
```

Перед запуском на уже работающем сервере убедитесь, что актуальная версия сценария соответствует существующей конфигурации.

Сценарий не должен использоваться как повод для удаления текущих контейнеров, захватов или пользовательских ключей.

### 5.3. Сборка лаборатории

`build-lab.sh` отвечает за создание или обновление контейнеров и сетей лаборатории.

Запускайте его в пользовательском контексте `dockerroot`, если именно так устроена текущая реализация:

```bash
sudo machinectl shell dockerroot@.host /bin/bash -lc \
  'cd /путь/к/network-lab && ./build-lab.sh'
```

Замените `/путь/к/network-lab` на фактический путь к репозиторию.

Перед повторной сборкой убедитесь, что нужные результаты экспериментов сохранены вне пересоздаваемых контейнеров. Не предполагайте, что данные внутри контейнера переживут его пересоздание.

### 5.4. Проверка состояния

```bash
sudo machinectl shell dockerroot@.host /bin/bash -lc \
  'docker ps --format "table {{.Names}}\t{{.Status}}"'
```

Должны быть видны три контейнера:

- `lab-client`;
- `lab-filter`;
- `lab-server`.

Проверьте сети и подключения контейнеров:

```bash
sudo machinectl shell dockerroot@.host /bin/bash -lc '
  docker network inspect lab-client-net
  docker network inspect lab-server-net
'
```

## 6. Участники и доступ

Предусмотрены три роли:

| Участник | Предполагаемая задача |
|---|---|
| `attacker` | Генерация экспериментального трафика и исследование методов обхода фильтрации |
| `defender` | Настройка и анализ механизмов фильтрации |
| `ml-searcher` | Исследование признаков трафика и подходов к его классификации |

Названия ролей описывают задачи в лаборатории, а не разрешение атаковать внешние системы.

### SSH-доступ

Для каждого участника должна быть создана отдельная учётная запись и добавлен индивидуальный публичный SSH-ключ.

Пример добавления участника:

```bash
sudo ./create-lab-users.sh attacker
```

Публичный ключ можно добавить позднее, повторно запустив соответствующий скрипт. Приватные ключи никогда не передаются администратору и не хранятся в репозитории.

Если в текущей конфигурации используется `lab-add-user`, применяйте эту команду вместо старого скрипта создания пользователей.

### Доступ к контейнерам

SSH-шлюз должен разрешать только заранее определённые операции, например:

- просмотр статуса лаборатории;
- открытие оболочки `lab-client`;
- открытие оболочки `lab-filter`;
- открытие оболочки `lab-server`.

Участники не должны получать доступ к Docker socket хоста или произвольное выполнение команд от имени `dockerroot` на хосте.

Root внутри контейнера не эквивалентен root на хосте, однако контейнеры остаются потенциальной границей риска. Поэтому следует использовать только необходимые привилегии и не подключать чувствительные каталоги хоста.

## 7. Работа с экспериментами

Рекомендуемый цикл эксперимента:

1. Подготовить или изменить конфигурацию.
2. Убедиться, что контейнеры запущены.
3. Запустить захват на `lab-filter`.
4. Сгенерировать контролируемый трафик с `lab-client`.
5. Проверить, что сервер получил запросы.
6. Остановить захват.
7. Проверить PCAP и сформировать метаданные.
8. Сохранить описание эксперимента и результаты.

### Пример: тестовый HTTP-запрос

В первом терминале запустите захват:

```bash
docker exec -it lab-filter \
  tcpdump -i any -nn -s 0 -w /captures/test-001.pcap
```

Предупреждение о promiscuous mode при использовании `-i any` само по себе не означает ошибку. Строка `listening on any` означает, что `tcpdump` начал захват.

Во втором терминале отправьте запрос:

```bash
docker exec lab-client \
  curl -v --connect-timeout 3 --max-time 10 \
  http://10.231.20.3:8080/
```

После завершения запроса остановите захват сочетанием `Ctrl+C`.

Проверьте содержимое файла:

```bash
docker exec lab-filter \
  tcpdump -nn -r /captures/test-001.pcap
```

Если PCAP пустой, проверьте результат `curl`, состояние сервера, интерфейсы фильтра и маршрутизацию.

### Важное замечание о сетевой маршрутизации

Наличие двух внутренних сетей Docker не гарантирует автоматически, что весь трафик клиента проходит через фильтр. Фактический маршрут зависит от IP forwarding, таблиц маршрутизации и правил фильтрации.

Это нужно проверять экспериментально и после каждого изменения сетевой конфигурации.

## 8. PCAP и метаданные

Каталог захватов на хосте:

```text
/srv/network-lab/captures/
```

В нём размещаются PCAP/PCAPNG и связанные файлы метаданных.

Рекомендуемый формат имени:

```text
YYYY-MM-DD-experiment-name-001.pcap
```

Для каждого эксперимента желательно фиксировать:

- дату и время;
- цель;
- конфигурацию фильтра;
- способ генерации трафика;
- использованные команды;
- ожидаемое и фактическое поведение;
- путь к PCAP;
- результаты анализа.

Для чтения метаданных может использоваться `capinfos`. Полноценный анализ пакетов выполняется в Wireshark или другом совместимом анализаторе.

Веб-каталог Caddy предоставляет доступ к файлам и их загрузке, если он соответствующим образом настроен. Он не заменяет полноценный браузерный анализатор PCAP.

## 9. Хранение и очистка результатов

Планируемая политика хранения:

- срок хранения захватов — 14 дней;
- целевой суммарный объём — не более 5 GiB;
- автоматическая проверка выполняется systemd-таймером.

**Ограничение:** логический лимит, реализованный скриптом очистки, не является жёсткой квотой файловой системы. Он не предотвращает заполнение диска между запусками таймера.

Если требуется гарантированное ограничение места, следует использовать отдельную файловую систему или поддерживаемую системой дисковую квоту.

Перед удалением результатов, необходимых для отчёта, сохраняйте их в отдельном защищённом хранилище.

## 10. Веб-доступ

Для публикации результатов используется Caddy с HTTPS и HTTP Basic Authentication.

Требования:

- домен указывает на VPS;
- HTTPS настроен и проверен;
- каждому участнику выданы индивидуальные учётные данные;
- каталог публикации ограничен захватами и метаданными;
- рабочая область и другие системные каталоги не доступны через веб-сервер.

Basic Authentication не следует использовать через незашифрованное HTTP-соединение для передачи реальных учётных данных.

Caddyfile зависит от версии Caddy. Например, в Caddy 2.6.2 используется директива `basicauth`; не заменяйте её на синтаксис из документации для более новых версий без проверки совместимости.

## 11. Безопасность

Запрещается:

- предоставлять участникам прямой доступ к Docker socket хоста;
- подключать каталог существующей библиотеки к экспериментальным контейнерам;
- хранить приватные SSH-ключи, пароли и реальные хеши паролей в Git;
- публиковать порты контейнеров без обоснованной необходимости;
- запускать эксперименты против чужих систем без разрешения;
- выполнять очистку или пересоздание контейнеров без проверки сохранности результатов;
- считать Rootless Docker абсолютной гарантией безопасности.

Экспериментальные контейнеры должны содержать только необходимые инструменты и данные. Не храните в общей рабочей области секреты или личные данные: все участники, имеющие доступ к общему тому, потенциально могут их прочитать.

## 12. Воспроизводимость и контроль изменений

Конфигурация лаборатории должна храниться в репозитории. Ручные изменения на сервере следует переносить в исходные скрипты и документировать.

После изменения сетей, правил фильтрации или контейнеров рекомендуется проверить:

- статус всех контейнеров;
- состав сетей и адреса узлов;
- отсутствие непредусмотренных опубликованных портов;
- отсутствие Docker socket в контейнерах;
- отсутствие подключения каталога библиотеки;
- доступность тестового сервера через фильтр;
- отсутствие непредусмотренного внешнего доступа;
- возможность записи и последующего чтения PCAP.

## 13. Устранение неполадок

### Контейнеры не запускаются

Проверьте:

```bash
sudo machinectl shell dockerroot@.host /bin/bash -lc \
  'systemctl --user status docker.service'
```

### HTTP-запрос не проходит

Проверьте:

```bash
docker ps
docker exec lab-filter sysctl net.ipv4.ip_forward
docker exec lab-filter ip -br addr
```

Затем проверьте логи и сетевые правила.

### PCAP пустой

Убедитесь, что захват начался до генерации трафика. Сам `tcpdump` пакеты не генерирует.

### Caddy не может читать файлы

Проверьте статус службы, фактического пользователя процесса, права на каждый родительский каталог и ACL. Не используйте `chmod -R 777` как способ исправления проблемы.

### Не работает SSH-доступ

Проверьте наличие публичного ключа в `authorized_keys`, права каталога `.ssh`, журнал SSH-службы и соответствие ключа ограниченной команде шлюза.

## 14. Лицензия и вклад в проект

До публикации репозитория укажите лицензию, если предполагается распространение проекта.

Изменения должны сопровождаться описанием цели, способа проверки и потенциальных последствий для изоляции лаборатории. Для сетевых изменений обязательно указывайте, как проверялось прохождение трафика и отсутствие непредусмотренных маршрутов.
